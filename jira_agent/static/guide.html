1. Ohne Code: Name, Regeln, Daten

  • Zahnrad oben rechts → Zugänge: Name des Agenten, Jira-Token (nur für diese Sitzung), optional eigener Azure-Key.
  • Regeln: in einfacher Sprache, z. B. „Tickets zu Bremsen ohne Bearbeiter gehen an chassis.lead“.
  • Datenquellen: Tabellen freigeben, die der Agent lesen darf (nur mit Ihren eigenen Rechten).
  • Mit Speichern übernehmen – gilt ab der nächsten Nachricht.

2. Eigenes Tool hinzufügen

Am einfachsten mit KI: Repo in VS Code öffnen und Copilot/Claude z. B. sagen: „Baue ein Tool, das den Status eines Tickets ändert.“ Die KI kennt die Regeln dieses Projekts (AGENTS.md), schreibt Tool und Test und kann deployen.

Von Hand: neue Datei in jira_agent/tools/ anlegen, z. B. mein_tool.py. Sie wird automatisch geladen. Vorlage: jira_agent/tools/example_custom_tool.py.

from jira_agent.tools import ToolContext, tool


@tool(write=True, needs=["jira"])          # ändert etwas -> Bestätigung nötig; nur mit Jira-Token
def jira_set_status(ctx: ToolContext, issue_key: str, status: str) -> dict:
    """Ändert den Status eines Tickets, z. B. 'In Arbeit' oder 'Erledigt'.

    issue_key: Ticket-Key, z. B. ABC-123
    status: Name des Statuswechsels oder Zielstatus
    """
    ctx.jira.transition(issue_key, status)
    return {"status": "OK"}
  • Docstring: erster Absatz = Beschreibung für das Modell, Zeilen name: Text = Beschreibung der Parameter. Typen kommen aus den Angaben wie str, int, list[str].
  • Erstes Argument ist immer ctx: ctx.jira (Jira mit dem Token des Nutzers – fertige Helfer: search, issue, create_issue, transition, assign, comment, set_priority, add_label, link, add_worklog, …), ctx.sql (lesendes SQL mit Nutzerrechten: ctx.sql.query(...), ctx.sql.describe(...)), ctx.files (Datei zum Download ablegen: ctx.files.put(name, mime, bytes) liefert eine URL), ctx.selected_tables (freigegebene Tabellen).
  • needs: "jira", "sql" oder "files" – das Tool ist nur sichtbar, wenn das vorhanden ist.
  • write=True für alles, was etwas verändert: Der Agent muss dann vorher „ja <CODE>“ einholen. Das ist im Code erzwungen, Sie müssen nichts weiter tun.
  • Rückgabe: ein dict. Fehler einfach als Exception werfen – der Agent bekommt sie als Text.
  • Bilder oder Downloads: im Ergebnis ein Feld "markdown" zurückgeben, z. B. f"![Titel]({url})" – siehe output_tools.py.
  • Testen ohne echtes Jira: Vorlage tests/test_example_custom_tool.py, ausführen mit uv run pytest tests -q.

4. Standardwerte ändern

jira_agent/config.yaml: Jira-URL, Azure-Endpoint und Deployment, Zeilenlimits, Standardregeln und Ablaufzeiten. databricks.yml unter variables: App-Name, Secret (Azure-Key) und Warehouse. Nutzer überschreiben Regeln, Name, Modell und Tabellen persönlich im Zahnrad.

5. Eigene Kopie der App / Deploy

  1. Repo kopieren (Fork) und in VS Code öffnen. Einmalig einrichten: Copilot/Claude sagen „Richte das Projekt ein.“
  2. In databricks.yml unter variables bei app_name einen eigenen Namen eintragen (z. B. agent-jira-team-x), ggf. Secret und Warehouse anpassen.
  3. Deployen: uv run deploy (oder der KI sagen „Deploye die App.“). Das legt die App mit allen Ressourcen und Scopes an, lädt den Code hoch und startet sie.
  4. In Databricks unter Compute → Apps → Name → Permissions festlegen, wer die App nutzen darf.
  5. Nach jeder Änderung erneut uv run deploy und die Seite mit Strg+Shift+R neu laden.

Die App mit einer Instanz und einem Worker betreiben: Keys liegen nur im Arbeitsspeicher und gehen bei Neustart oder Deploy verloren.

MLflow-Traces enthalten Chat-Inhalte (auch Ticket-Texte und Abfrageergebnisse, keine Keys) – Zugriff auf das Experiment restriktiv vergeben.

6. Sicherheitsregeln

  • Keine Keys oder Tokens in Code, Logs, Tool-Ergebnissen oder settings.json.
  • Alles, was in Jira oder anderen Systemen etwas ändert, mit write=True markieren.
  • SQL nur über ctx.sql und check_readonly_sql (nur SELECT, nur freigegebene Tabellen, nur eingebaute Funktionen – kein ai_query, http_request, secret, keine UDFs).
  • Eingaben prüfen, z. B. JiraClient.check_key() für Ticket-Keys.
